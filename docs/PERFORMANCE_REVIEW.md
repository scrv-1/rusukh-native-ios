# مراجعة الأداء وحدود القياس

المراجعة مبنية على المصدر وسجلات Run 14 ثم إعادة التحقق Run 18؛ ليست جلسة Instruments على iPhone. استُخدمت مهارة [SwiftUI Performance](https://github.com/dpearson2699/swift-ios-skills/blob/8d90fd121a263355a4fb44fd082af1416a5c1c2a/skills/swiftui-performance/SKILL.md) المقروءة عبر omgskills عند الالتزام المثبت، وطابق محتواها hash الفهرس. لم يُثبت برنامج خارجي أو تُنفذ سكربتات المهارة. يميز هذا التقرير التحذير المثبت عن فرضية التكلفة المستنتجة من الكود.

| القياس الفعلي | النتيجة | ما لا يثبته |
|---|---|---|
| بحث 1000 ملاحظة، XCTest Mac، Run 14 | متوسط 0.025s، RSD 49.975% | ليس زمن بحث واجهة Release على الآيفون؛ التشتت كبير ولا baseline مقارن |
| قمة عملية XCTest | نحو 388428kB بعد اختبارات JSON كبيرة | ليست ذاكرة التطبيق أو MLX أو كل اختبار معزولًا |
| 4 رحلات XCUITest في Simulator | 178.099s، 0 فشل، 0 تخطي | ليست سرعة تفاعل المستخدم؛ تتضمن الانتظار والأتمتة |
| جلسة الصوت | Run 18: لا runtimeWarnings وعدّاد AVAudioSession الرئيسي صفر؛ 7 وحدات متحكم ورحلتان صوت في UI نجحت | لا قياس لمدة hitch أو جودة ميكروفون الهاتف |
| استدلال Swift Mac الحالي، Run 15 | أول جواب مع التحميل 7.60s، البقية 0.34–1.55s؛ قمة pool تراكمية 2,564,247,224 بايت، active بعد unload 4064 وcache صفر | ليس RSS أو زمن iPhone؛ probe يحتفظ بالمحرك بين الأسئلة، وواجهة الهاتف تفرغه بعد الطلب |
| بطارية وحرارة وNeural Engine | غير مقاسة | لا تستنتج من Simulator أو Mac Metal |

أولويات قبل اعتماد إنتاجي:

1. **تحذير عولج في الرحلات المختبرة:** نقلت تهيئة جلسة الصوت وكائنات recorder/player وبدءها إلى طابور متسلسل بملكية UUID وإلغاء مرتب. نقل setActive وحده أبقى تحذيرين في Run 16؛ الإصلاح المكمل اجتاز Run 18 مع runtimeWarnings فارغة. اختُبرت حالات الإغلاق المتأخر والخلفية وإعادة التسجيل. لا يزال قياس Hangs/Hitches والمقاطعات على هاتف مطلوبًا؛ غياب التحذير ليس قياس أداء كاملًا.
2. **فرضية من الكود:** `LibraryStore.init/commit/importFromFile/exportToTemporaryFile` تقرأ/تكتب JSON متزامنًا على MainActor. مع حد 80MB ومرفقات مضمّنة قد يتأخر الإطلاق والحفظ. نقل التخزين إلى actor تغيير متوسط/كبير يحتاج الحفاظ على ترتيب commits، وعدم إعلان نجاح قبل الكتابة، واختبار فشل القرص والاستيراد المتزامن. لا توجد قيمة hitch مقاسة حتى الآن.
3. **فرضية من الكود:** `NotesView.results` يرتب ويبحث عند تقييم الواجهة، ويتكرر استخدامه للحالة الفارغة؛ صف الصورة يفك UIImage من البيانات. تحسين صغير/متوسط بعد trace: نتائج مشتقة تتحدث عند تغير النص/الملاحظات وصور مصغرة محدودة الحجم. هويات ForEach الحالية ثابتة من نموذج الملاحظة؛ لا دليل churn من UUID صف جديد.
4. **فرضية من الكود:** `GraphView` يحسب graphEdges داخل GeometryReader ومرة أخرى لعداد العلاقات؛ السحب والتكبير يغيران state وقد يعيدان الحساب. تحسين صغير/متوسط: اشتقاق الحواف عند تغير الملاحظات مع بقاء المواضع مرتبطة بقياس العرض. لا تقسيم بنيوي كبير دون قياس؛ اختبار 1000 عقدة يحتاج قياس كثافة الرسم والوصول أيضًا.
5. **قيد تجربة النموذج:** cache 64MiB وحدود الرموز تقلل النمو غير المحدود، لكنها لا تضمن البقاء تحت حد iOS. يلزم قياس cold/warm start وذروة RSS الفعلية والخلفية/الإلغاء والتحذير الحراري على هاتف 8GB مؤهل. قياس Mac pool، إن نجح، منفصل عن RSS والطاقة.

خطة قياس الجهاز عند إتاحته: Release، نفس البيانات والسيناريو قبل/بعد، Instruments SwiftUI وTime Profiler وHangs/Hitches، وقياس ذاكرة العملية والطاقة مع تسجيل طراز الهاتف وiOS وحالة الشحن والحرارة. لم يُطلب من المستخدم شراء Mac أو خدمة مدفوعة؛ غياب الهاتف المقترن يمنع القياس الآن. تبقى هذه البنود مفتوحة؛ نجاح اختبارات الوظائف لا يجعل الأداء إنتاجيًا.

اختبار ضغط FSRS محلي إضافي: 1000 بطاقة و32000 مراجعة، 32 نسخة كاملة وإعادة قراءتها، 7.877 ثانية على Linux Debug. هذا زمن اختبار صحة بيانات يشمل الترميز والمقارنات، لا زمن عملية واجهة أو مقارنة عادلة لـSQLite، ولا قياس موارد هاتف.
